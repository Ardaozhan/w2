# W2 — Phase 02: Evidence Engine & Run Receipt

## Status
**Gate:** BLOCKING  
**Prerequisite:** Phase 01 must be COMPLETE.

---

## 1. Objective

Turn raw run data into trustworthy, structured evidence.

This phase creates the W2 product core:

> **Run Receipt**

The Run Receipt must answer:

1. What task was attempted?
2. What context did the agent receive?
3. What actions occurred?
4. What code changed?
5. What verification ran?
6. Which acceptance criteria are proven?
7. Why is the outcome PASS, FAIL, or UNPROVEN?

---

## 2. Evidence Model

Define evidence as structured records.

Minimum evidence types:

```text
CONTEXT_EVIDENCE
TOOL_EVIDENCE
DIFF_EVIDENCE
TEST_EVIDENCE
LINT_EVIDENCE
TYPECHECK_EVIDENCE
BUILD_EVIDENCE
ASSERTION_EVIDENCE
MODEL_INTERPRETATION
```

Every evidence item must contain:

```text
evidence_id
run_id
type
source
summary
raw_reference
confidence_class
created_at
```

---

## 3. Evidence Classes

Use explicit trust classes.

### Deterministic
Generated from:

- git
- command exit codes
- tests
- file assertions
- tool runtime
- stored events

### Interpreted
Generated by GPT-5.6 from existing evidence.

The UI and receipt must distinguish these classes.

---

## 4. Acceptance Criterion Model

Each criterion must have:

```text
criterion_id
description
required
status
evidence_ids
reason
```

Status:

```text
PASS
FAIL
UNPROVEN
```

---

## 5. Evidence Mapper

Use GPT-5.6 to map evidence to acceptance criteria only where interpretation is required.

Input must contain:

- criterion
- relevant deterministic evidence
- task constraints
- optionally relevant diff excerpts

The model output must follow a strict schema.

Example:

```json
{
  "criterion_id": "AC-02",
  "status": "UNPROVEN",
  "reason": "Tests passed, but no evidence verifies the required 429 response.",
  "evidence_ids": ["ev_12", "ev_17"]
}
```

The model must not invent evidence IDs or deterministic facts.

Validate every referenced evidence ID.

---

## 6. Outcome Engine

Final outcome must be deterministic based on criterion states.

Recommended rule:

```text
if infrastructure_error:
    ERROR
else if aborted:
    ABORTED
else if any required criterion == FAIL:
    FAIL
else if any required criterion == UNPROVEN:
    UNPROVEN
else:
    PASS
```

The model must not directly choose the final run outcome.

---

Example top-level shape:

```text

run_id
task
agent
context
actions
changes
verification
acceptance

generated_at
```

Provide:

- JSON representation
- human-readable representation

---

## 8. Human-Readable Receipt

Example structure:

```text
W2 RUN RECEIPT

RUN
w2_0184

TASK
Implement rate limiting

CONTEXT
14 files considered
6 files supplied

ACTIONS
23 tool calls
4 files modified

CHANGES
+183 / -31

VERIFICATION
PASS tests
PASS lint
PASS typecheck

ACCEPTANCE
PASS AC-01
FAIL AC-02
UNPROVEN AC-03

OUTCOME
FAIL

WHY
Required criterion AC-02 is contradicted by verification evidence.
```

The receipt must prioritize clarity over decoration.

---

## 9. Receipt Integrity

Every receipt value must be traceable to stored data.

Requirements:

- evidence IDs are valid
- run ID exists
- diff references exist
- verification references exist
- criterion evidence references exist

Add an integrity validator.

A receipt failing integrity validation must not be presented as final.

## 11. Failure Cases

Create explicit tests for:

1. agent says done, test fails
2. all tests pass, criterion lacks evidence
3. criterion contradicted by deterministic assertion
4. model references nonexistent evidence
5. verification not configured
6. infrastructure error
7. receipt integrity failure

---

## 12. Demo Fixture

Create the first competition-grade fixture.

Recommended:

> Implement login rate limiting:
> - max 5 attempts per minute
> - return HTTP 429 after limit
> - existing auth tests remain green

The fixture should allow at least one plausible implementation that passes tests but fails or leaves one criterion unproven.

Do not fabricate the failure. The scenario must be reproducible.

## 14. Acceptance Criteria

### Evidence
- [ ] Evidence schema is versioned.
- [ ] Deterministic vs interpreted evidence is explicit.
- [ ] Every evidence item has a valid source.

### Acceptance Mapping
- [ ] Criteria are represented individually.
- [ ] GPT output is schema validated.
- [ ] Unknown evidence IDs are rejected.
- [ ] Missing evidence results in `UNPROVEN`, not PASS.

### Outcome
- [ ] Final outcome is computed deterministically.
- [ ] Model cannot override the outcome engine.
- [ ] Required criterion FAIL causes final FAIL.
- [ ] Required criterion UNPROVEN prevents PASS.

### Receipt
- [ ] JSON Run Receipt exists.
- [ ] Markdown Run Receipt exists.
- [ ] Receipt schema version exists.
- [ ] Receipt integrity validator exists.
- [ ] Every public field is traceable to stored run data.

### Regression
- [ ] False-DONE case is tested.
- [ ] UNPROVEN case is tested.
- [ ] Invalid evidence reference is tested.
- [ ] Receipt integrity failure is tested.
